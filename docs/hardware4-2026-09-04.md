# YDE unified-hardware4: provenance, fixes, and testing

This is a YDE-based integration, **not** a new merge from upstream ZealOS master.
It is a test candidate, not a claim that every platform or native SMP is fixed.
Steve subsequently requested removal of the native single-core guard: this
build intentionally enables multicore on the Mac mini as an experiment.

## Confirmed regressions and changes

### ATAPI reads could corrupt the compiler

`e30cfe7c` introduced the 128-block (64 KiB) ATAPI cap without the older
multi-window read loop. `BlkRead` callers can still request an entire file.
The old implementation read about 132 KiB into a temporary buffer and then
copied a caller-sized amount, including the 196,880-byte Compiler.ZXE.

In a disposable QEMU boot of hardware3, the compiler's header was valid but
its patch table contained allocator-fill bytes. The `ExeFile` import in
KMain remained unresolved; the system task reached its server wait rather
than doing useful compilation. This explains why "Load(Compiler)" could stay
on screen indefinitely. It is not evidence that YDE needs hours to compile.

The new loop reads whole optical sectors in bounded windows, copies only
bytes actually in that window, reuses one buffer, checks DMA byte counts,
handles unaligned logical-block requests and EOF, and frees on exceptions.
KMain also rejects a compiler load that did not publish its `ExeFile` export.

### UTM's default input bus was lost in controller selection

The inspected UTM q35 configuration uses `i8042=off`, a legacy `-usb` bus for
its built-in usb-kbd/mouse/tablet, and a separate NEC xHCI controller for USB
redirection. The UI's "USB 3.0" setting does not imply those built-in HID
devices are attached to the NEC controller.

The integration probed UHCI and then EHCI, but chose UHCI on equal coverage.
By then EHCI had claimed the companion ports. Runtime debugging observed
EHCI input flags `3` (keyboard + pointer), followed by final flags `0` after
the losing reinitialization. Hardware4 restores EHCI tie priority and keeps
its already-initialized queues. It does not replace YDE's native xHCI driver.

KbdInit/MouseHardDriverInstall now skip an absent i8042 (status 0xFF) rather
than waiting for PS/2 commands to time out. KMain recognizes legacy USB mouse
ownership as well as xHCI when publishing the initial input state.

QEMU's ownership implementation provides supporting context:
<https://github.com/qemu/qemu/blob/master/hw/usb/hcd-ehci.c>

### USB mass-storage DMA safety

The existing one-TRB 64 KiB transfer size is retained, but its bounce buffer
is now 64 KiB aligned. CBW/CSW buffers are 64-byte aligned. A single normal
TRB must not cross a 64 KiB address boundary; limiting its length alone does
not ensure that. See the primary implementation reference:
<https://github.com/torvalds/linux/blob/master/drivers/usb/host/xhci-ring.c>

Short block transfers and truncated CSWs now fail instead of returning stale
bounce-buffer data or reporting a partial write as complete. This is a
safety fix, **not a measured explanation of the entire 36-hour install**.

### Build-only startup queue leaked into the UEFI ISO

After the controlled read/USB experiment reached the splash and accepted
Return, hardware3 attempted to run AutoFullDistro4. Its UEFI staging tree
contained `Home/Registry.ZC` with that build-only Once queue. The BIOS distro
builder already removes its registry; the separate UEFI packager did not.

The UEFI packager now deletes that generated registry from its private staging
tree. This preserves root `Once.ZC` and the normal live/install prompt. It
does not delete a user's installed registry or bypass the splash.

## What remains unchanged or unproven

- YDE's desktop, splash and browser remain part of the source. No new splash
  bypass, forced automatic installation, PS/2-only mode, or network redesign.
- Later TG3/BCM57766 receive and DHCP work and Apple Trackpad2 support remain.
  Their physical-hardware behavior still requires Steve's test.
- All platforms, including the native BCM57766 Mac mini, now attempt normal
  multiprocessor startup after compiler linking unless CONFIG_NO_MP was
  explicitly selected. The Mac mini detection guard is removed. This is an
  experiment, not proof that its earlier timer/AP/interrupt faults are fixed;
  a native crash or hang is a possible test result. Device polling/audio
  quirks are not changed merely because the APs are enabled.
- Ethernet polling is not blindly replaced with interrupts. Earlier native
  interrupt-routing failures affected USB; throughput and input latency need
  measurements before changing that policy.
- A bounded BOT driver is not UAS or queued asynchronous storage. Do not
  advertise "super fast USB" until transfer tests demonstrate it.

## Validation before the full rebuild

- Disposable KVM/Q35 UEFI test, hardware3 ISO, no host or guest hard disk:
  raising the ATAPI read window in guest RAM allowed compiler linking and
  reached the normal spinning YDE splash.
- Repeating with UTM-style companion-bus HID and no i8042, retaining EHCI
  state in guest RAM preserved keyboard + pointer flags and Return dismissed
  the splash. This is controlled diagnostic evidence, **not** a boot test of
  the new source or Apple Silicon TCG.
- `python3 utils/test_hardware4.py`: executes the actual new ATAPI loop under
  host ASan/UBSan with mocked I/O (only HolyC catch syntax is translated).
  1,188 aligned/unaligned, compiler-sized, large-file, EOF and short-read/error
  cases pass. Other checks cover selection, boot ordering, DMA and packaging.
- `git diff --check` and `sh -n build/build-iso.sh`.
- The disposable diagnostic QEMUs were stopped. User VMs were not stopped.

## Detached Mac mini build and test order

Build host: `ssh steve@192.168.4.48` (Omarchy).
Dedicated checkout: `/home/steve/ZealOS-yde-unified-hardware4`.
Unit: `yde-unified4-build.service`; log: `build/unified4-build.log`.
The checkout's `git rev-parse HEAD` is the exact source revision.

The full build uses a private 1 GiB raw disk, KVM and four vCPUs, and produces
both `build/ZealOS-BSD2-UEFI-*.iso` and `build/ZealOS-PublicDomain-BIOS-*.iso`.
The private build scratch directory is on /home, not the crowded /tmp tmpfs.
The required mtools package is extracted into this build's private work/tools
directory; no system-wide package installation is required.
No physical installation disk is attached to the build VM. The old build
checkouts/ISOs are preserved. The build continues independently of SSH.

After it finishes, test these before native installation:

1. UTM q35, USB3, Force PS/2 off: boot the new UEFI ISO; Return should dismiss
   the splash into the normal install question. Say **No** for the live test.
2. Check typing, clicks, relative mouse and seamless absolute-tablet movement,
   including after changing UTM cursor capture mode.
3. Repeat in virt-manager q35/UEFI with xHCI USB keyboard/mouse/tablet and SATA
   optical/disk devices. Also test an ordinary PS/2 input configuration.
4. Install only to a new disposable virtual disk; verify the target before
   accepting formatting. Eject the ISO and check installed boot/input.
5. Test one and multiple vCPUs. Record boot time, copy progress/time and input
   responsiveness instead of inferring performance from a paused screenshot.
6. Then native Mac mini: live boot first, keyboard, Trackpad2, DHCP and ping
   replies, and finally a controlled storage copy with timings. Record the
   detected CPU count and any AP/timer fault; native SMP is experimental.

"Finished" and both output files mean the build completed, not that the above
hardware tests passed. Do not install over the working native disk merely
because the build exited successfully.

The Omarchy graphical login keeps the user service manager alive after SSH
disconnects. Linger is not enabled (changing it requires sudo), so leave
Omarchy logged in and the host awake while this build runs.
